The decline is the brand. Every payments demo in this space shows a purchase succeeding; the product here is the refusal — decided inside the issuer's synchronous window, recorded on the same hash-chained feed as the successes. And the agent held only last4 4242 the whole time: no card number appears in the transcript, and the pinned demo test proves nothing PAN-shaped ever does.

Issuing reserves, spending clears

A reserved card sets its full cap aside from the agent funds before it works. Close the card and the unspent remainder returns; mandate authority already used is never restored. No surprise bills, by arithmetic.

Answered live, at the network

Every authorization is answered synchronously by a fixed decline ladder — merchant category, allowlist, merchant lock, single-use, first-merchant throttle, cap — inside the issuer's two-second deadline.

Your agent never sees the card number

The MCP tools return only the last4. In token mode the host runtime — never the model — redeems a single-use checkout token outside model context. Default mode has no reveal surface at all.

Act 2 · the closed loop and x402

The same mandate governs API payments — and refuses the same way.

The card rail is one act. The other: an agent buys a $0.05 report over HTTP 402 inside its mandate, then tries a $1.50 upgrade. The network — not the model — says no. This is the actual decision object the policy engine returns.

claude — agent session
# mandate mnd_7f3a — budget $10 · per-tx $1 · daily $5 · ask-me-above $2 · new-payee 10¢ · expires 30d

> Buy the market report from @research-cloud, then upgrade us to the premium dataset.

⏺ money_fetch(url: "https://api.research-cloud.example/report")
  ⎿ HTTP 402 → paid $0.05 under the mandate · receipt rcpt_01j8k…
     200 OK — report delivered

⏺ money_pay(to: "@research-cloud", amount_usd: 1.50, memo: "premium dataset")
  ⎿ {
       "status": "denied",
       "code": "per_tx_cap",
       "reason": "$1.50 exceeds the $1.00 per-transaction cap"

The refusal is the product. The mandate lives in the network's policy engine, outside every model context — injected text can ask, but nothing an agent reads can sign a payment or widen its own envelope. Above the ask-me line, the agent doesn't get a no; it gets a durable approval_required request, and the owner approves the exact stored payee-amount-memo tuple. What the human saw is what executes.

Deterministic policy

One grant line. Enforced to the micro-dollar.

grant: budget $10 · per-tx $1 · daily $5 · ask-me-above $2 · new-payee first-touch 10¢ · expires 30d

Escalation line

Above the ask-me line, the payment becomes a durable approval request in the owner's inbox. Approving executes that immutable tuple through a one-time permit — no gap between what the human saw and what runs. Requests survive restarts and recover exactly once across a crash at settlement.

New-payee throttle

The first payment to any unseen payee is capped at cents — including external x402 vendors, keyed on canonical host plus destination address. A prompt-injected agent lured to an attacker's endpoint can leak cents per day, not the envelope.

Allowlists

Pin a mandate to exact payees. Everything off the list is refused with payee_not_allowed before it touches a balance or a rail.

Single-use permits

Every authorized payment mints a permit bound to (agent, payee, amount) with a 60-second TTL, used once. Replay and amount inflation are structurally dead, not detected after the fact.

Hash-chained receipts

Every payment appends to a tamper-evident evidence log. Refunds tie to the original receipt, cannot exceed the purchase, and never restore mandate budget — so a cooperating buyer and seller cannot recycle an agent's spending authority.

Exactly-once by construction

Idempotency keys on every transfer; 402 challenges are pay-once, redeem-once. Agents retry by default — an exact retry returns the original receipt, never a second charge.

The wallet

Seven tools. That's the whole surface an agent gets.

@agentmoney/wallet-mcp works in Claude Code, Cursor, or any MCP-capable runtime. The agent process holds only its own signing key — never the owner key, and never a spending decision. Every payment is policy-checked server-side.

ToolWhat it does
money_balance Spendable balance and mandate state.
money_pay Pay any account — agent, provider, or user — by id or @handle, idempotency-keyed.
money_fetch GET a URL; on HTTP 402 (network challenge or external x402 seller) pay it within the mandate and retry — exactly-once, crash-recoverable. HTTPS required, redirects never carry payment credentials, private targets rejected by default.
money_card_create A reserved virtual card under the owner's spend mandate, for buying at an ordinary online merchant. Issuing reserves the full cap up front; returns only the last4 — the tool never sees or returns the card number. Caps above the owner's escalation line become a durable approval request instead.
money_card_status One card's state, cap, what has cleared at the merchant, and whether the owner has approved it yet.
money_card_close Close a reserved card. The unspent remainder returns to the agent funds; mandate authority already used is not restored.
money_feed Recent receipts — the hash-chained evidence feed, both rails.
Quickstart — agent side

One block of JSON, and your agent has a wallet.

Add this to .mcp.json. Your beta invite comes with the three values: the hosted network URL, an agent id, and a key file. (Or run the whole network yourself from the open-source repo — its onboarding prints this exact config.) 

{
  "mcpServers": {
    "money": {
      "command": "npx",
      "args": ["-y", "@agentmoney/wallet-mcp"],
      "env": {
        "MONEY_API": "https://url-from-your-invite",
        "MONEY_AGENT_ID": "agt_xxxxxxxx",
        "MONEY_AGENT_KEY_FILE": "/absolute/path/to/agent.key"
      }
    }
  }
}

The key stays in a file, out of .mcp.json and out of every model context. Then ask your agent to check its balance.

Quickstart — seller side

Charge agents for your API in one middleware.

@agentmoney/seller-sdk is a Hono paywall plus a signed client for challenges, receipt redemption, and refunds. Zero runtime dependencies. Prices come from your registered service — the network is authoritative, so a compromised route can never invent one. 

import { Hono } from "hono";
import { moneyPaid, secretFromEnv } from "@agentmoney/seller-sdk";

const providerKey = secretFromEnv("MONEY_PROVIDER_KEY")!; // reads MONEY_PROVIDER_KEY_FILE

const app = new Hono();
app.get("/report", moneyPaid({
  networkUrl: process.env.MONEY_API!,
  providerId: process.env.MONEY_PROVIDER_ID!,
  providerKey,
  serviceId: process.env.MONEY_SERVICE_ID!,
}), (c) => c.json({ report: "valuable machine-readable result" }));

Unpaid requests get a 402 challenge issued by the network at your registered price; the middleware redeems the agent's receipt — pay-once, redeem-once — before your handler runs. Refunds are partial or full, idempotent, and capped at the original purchase.

Status, honestly

What this is today — and what it isn't.

  • Invite-only, testnet-labeled beta. Sandbox balances with hard caps and no KYC. Explicitly not production; do not point real budgets at it.
  • The card rail is sandbox today. The demo above runs against a Stripe-shaped mock issuer. The Stripe Issuing integration is protocol-faithful, fixture-tested, and test-mode ready — there is no live card program and no real card. Sandbox, no real funds.
  • x402 mainnet: implemented, not yet switched on. The external x402 rail is built and tested; mainnet activation is gated on a ~$15 founder float. Until then it runs in sandbox.
  • One free-tier VM, best-effort. Nightly encrypted backups and external monitoring, but no SLA. The status page says exactly this.
  • Real numbers or no numbers. We publish wash-proof metrics from the receipts journal — funding lineage, retention cohorts, chain roots. If a number is zero, it says zero.
  • The code is the claim. Apache-2.0, every invariant tested, including a live-Postgres release gate that races concurrent connections against one spending cap. Read it before you trust it.
  • Fail-closed is the brand. External rails, funding, and compliance routes refuse to operate rather than operate ungoverned. Incidents get published post-mortems.
